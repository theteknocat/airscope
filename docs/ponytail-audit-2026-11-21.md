# Ponytail audit, 2026-11-21 (follow-up)

This is the second pass of the audit I started on 2026-11-20 (see `ponytail-audit-2026-11-20.md`), run with Claude Code using the ponytail audit skill. That first pass was partial, so this one covers the code it said it hadn't read. Scope for this round: the code that reads data from outside the app (`src/nl80211.rs`, `src/nm.rs`, `src/bluez.rs`, `src/picker.rs`, `src/net.rs`) and every `unsafe` block in the rest of `src/`. Nothing here was run on hardware other than my own machine, and apart from finding 2, which I did try by hand, I haven't triggered any of these findings, they come from reading the code.

## Findings

1. **The router can lose its router icon behind a VPN** (`src/net.rs`, minor, fixed). `gateway()` picks the default route with the lowest metric and doesn't look at whether it has a gateway address. A VPN that adds a default route straight onto its own interface has the address `0.0.0.0`, so if that route wins on metric the "gateway" comes back as `0.0.0.0` and the real router is no longer marked as the gateway in the LAN list. **Fixed.** `gateway()` now skips default routes with no gateway address. I didn't add a test because the function reads `/proc/net/route` directly, and I haven't tried it with a VPN up.

2. **Two file dialogs at once could clash** (`src/picker.rs`, minor, fixed). Every dialog asks the desktop portal for the same request name (`airscope` plus the process id). The save button and the vendor import button each refuse a second click while theirs is open, but Open in Diagnostics, Export and the vendor import don't check each other, and the dialogs aren't modal. I haven't confirmed what the portal does with a duplicate name. I did try it by hand on KDE Plasma (Wayland): I opened the vendor import's file dialog, brought the app back to the front, closed the vendor window, went to Diagnostics and opened a capture file dialog as well. Both dialogs stayed open and both could be cancelled with no error, so on KDE the clash does no harm. **Fixed anyway.** Each dialog now gets its own request name (the process id plus a counter), which is safe whatever another desktop's portal does. The bigger thing this showed is that the dialogs aren't modal, so the app can be used while one is open. That is a separate item (see finding 7).

3. **A 6 GHz access point on channel 2 gets a nonsense channel number** (`src/nm.rs`, minor, fixed). `channel()` takes 5950 off the frequency for anything from 5925 to 7125, but channel 2 sits at 5935 MHz, so the subtraction goes below zero. A release build wraps round to a number around 859 million and shows it as the channel, and a debug build panics. It needs an access point on that one channel, which is rare, and the test only covered channel 1. **Fixed.** Channel 2 (5935 MHz) now has its own case, anything else below 5950 MHz counts as "not a channel" (0) instead of wrapping, and the test covers both.

4. **A device could list "Human Interface Device" twice** (`src/bluez.rs`, minor, fixed). The service list is tidied with `dedup()`, which only removes neighbours, but two different UUIDs (`1124` and `1812`) share that name and BlueZ doesn't keep them side by side. It would take a device that offers both. **Fixed.** The list now drops repeats anywhere in it, keeping the order, and I removed the second, redundant `dedup()` in `src/data.rs`. No test, since `devices()` needs a live BlueZ, and I don't own a device that offers both.

5. **The same three lines for local time are copied seven times** (`src/snoop.rs` three times, `src/capture.rs`, `src/data.rs`, `src/diag.rs`, `src/dtpick.rs`, minor, fixed). Each one makes a zeroed `tm` and calls `localtime_r` inside an `unsafe` block. One small helper would leave a single `unsafe` block to check instead of seven. **Fixed.** There is now one `snoop::local()` that holds the only `localtime_r` call, and the other six places use it. The existing date tests still pass, and the app's own dates and clocks go through the same code.

6. **One test changes `HOME` for the whole test run** (`src/data.rs`, minor, fixed). `oui_import` calls `set_var("HOME", ...)` while other tests run on other threads, and changing the environment while another thread reads it is not safe. I haven't seen it fail, so it's a flaky-test risk rather than a bug in the app. **Fixed.** The vendor list now keeps its own file path (`Oui.user`), the test points it at a temp folder, and no test touches the environment any more. I checked that my real `~/.config/airscope/` was left alone.

7. **The app stays usable while a file dialog is open** (`src/picker.rs`, `src/main.rs`, `src/diag.rs`, `src/diag/page.rs`, minor, fixed). Found by hand while testing finding 2. The desktop's file dialogs aren't attached to the Airscope window (`parent_window` is empty), so on KDE you can carry on using the app behind one. You can close the vendor window and open a second dialog from Diagnostics, or pick a file in a dialog whose window has already gone. If you open a capture dialog first and then the vendor window, the vendor window ends up under its own dark cover, which happens to stop a second dialog but isn't deliberate. **Fixed in the app.** I checked that a Wayland window can't hand the portal a handle to attach the dialog to (eframe doesn't give one), so while any file dialog is open the whole window is dimmed, ignores clicks and says "Waiting for the file dialog…", with a "Cancel" button that asks the portal to close the dialog (the same as its own Cancel), and forgets a dialog the portal can't reach so a lost one can't lock the window. Escape no longer closes the vendor window while its dialog is open. It compiles and the tests pass, but I haven't tried it with a real dialog, and it can't force the dialog above the window, only stop the app being used meanwhile.

## Looked at and left alone

- **The `unsafe` blocks themselves.** The socket, `ioctl`, `poll`, `read`, `write`, `localtime_r` and `mktime` calls all check their results or can't fail in a way that matters, the buffers are sized by the code that fills them, and the netlink and HCI parsers check lengths before they index. I found no memory problem.
- **Reading the kernel's replies** (`nl80211.rs`, `net.rs`, `hci.rs`). A short or cut-off message stops the parse and returns what it has instead of panicking.

## Not read

The rest of `src/data.rs` beyond its `unsafe` lines, `src/syslog.rs`, `src/diag/logview.rs`, all of the drawing code in `src/main.rs`, `src/fx.rs`, `src/diag.rs` and `src/diag/page.rs`, and `src/demo.rs`. Those are the next scopes.

## Verdict

Seven findings, all minor, and none of them a way to lose data. All seven are fixed. Findings 1, 3, 4 and 6 are small code changes, 2 and 5 tidy up shared code, and 7 came out of testing 2 by hand and is the only one that changes how the app behaves. The file dialog block and its Cancel button are the part I'd still want more people to try, since I've only used them on KDE Plasma under Wayland. The code that reads from outside the app (netlink, D-Bus, the portal) was in decent shape, and I found no memory problem in any `unsafe` block.
